# ЛР1 — Nginx, HTTPS и два backend

Nginx обслуживает статический интерфейс по HTTPS и распределяет API-запросы между двумя экземплярами Flask. В текущем Compose четыре сервиса: frontend с Nginx, `backend`, `backend2` и отдельная PostgreSQL. Каждый backend подключён к сетям `frontend` и `database`; frontend не входит во внутреннюю сеть БД.

Критерий успеха — не просто открывшаяся страница. Нужно увидеть оба backend, проверить поведение маршрутов и показать, что остановка одного экземпляра не лишает API второго.

## Локальный запуск

Используйте [единый быстрый запуск проекта](../../README.md#запуск): сначала создаётся `.env`, затем локальные TLS/Basic Auth файлы и Compose-стек. Эти файлы нужны до запуска Nginx; одного `docker compose up` в свежем checkout недостаточно.

## Что проверяется

```sh
./scripts/lab-01-check.sh
./scripts/lab-01-dns-check.sh
```

Первый скрипт проверяет редирект HTTP→HTTPS, появление обоих значений `X-Backend-ID`, `/docs/` с `alias`, выдачу разного содержимого по `app.local` и `companion.local`, собственные 404-страницы, Basic Auth, разрешённые публичные файлы в `/assets/`, ответ 429 на короткий burst запросов и доступность API при остановке `backend2`. После теста второй backend запускается обратно. Второй скрипт в собственной временной сети меняет backend IP и проверяет, что Nginx узнаёт его без reload; скрипт удаляет созданные им контейнеры и сеть.

В DNS-опыте Nginx нашёл новый адрес backend без reload. Первый запрос при этом истёк по трёхсекундному таймауту, следующий вернул 200 с новым upstream. Автоматика избавила оператора от ручной перезагрузки. Небольшую паузу она тоже организовала самостоятельно. Поэтому здесь проверена смена адреса без reload, а непрерывная доступность не заявляется.

Точки настройки: [Nginx](../../docker/lab-01/nginx.conf), [Compose](../../compose.yaml), [идентификатор backend](../../app/backend/server.py). Секреты TLS/Basic Auth создаются скриптом в `.local/nginx/`, исключённом из Git.
