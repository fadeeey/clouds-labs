# ЛР2* — устойчивость и лимиты

Проверены возвращение сервиса после отказа БД и работа приложения при ограниченных ресурсах. Опыт 20 октября показывает восстановление и первоначальные измерения. В отдельном опыте 28 октября нагрузка идёт через API настоящего backend: зафиксированы CPU throttling, контейнерный OOM и рабочий лимит. Успех восстановления определяется не только состоянием процесса: API должен снова прочитать сохранённую запись.

## Самовосстановление — 20 октября 2026 года

В `compose.yaml` у `db`, `backend` и `frontend` настроены healthcheck/restart, а зависимости используют `condition: service_healthy`. Для проверки остановил PostgreSQL внутри контейнера командой `pg_ctl ... stop -m immediate`. Политика Compose перезапустила контейнер; `docker inspect` показал `restart_count=1`, health БД вернулся в `healthy`, а `/healthz` ответил `{"database":"ok","status":"ok"}`. После восстановления API вернул прежние записи, в том числе задачу с ID 6. Данные в именованном томе сохранились.

Здесь подтверждены один отказ БД, её перезапуск и повторное чтение задачи с ID 6 в локальной конфигурации этого опыта. Политика restart возвращает процесс, health проверяет доступ к БД, а чтение записи — сохранность конкретных данных. Ни один из этих признаков не заменяет остальные; гарантия для произвольного сбоя или другого хоста из опыта не следует.

## Первоначальный опыт с лимитами — 20 октября 2026 года

Для сервисов выставлены лимиты: БД — 0,50 CPU / 256 MiB, backend — 0,50 CPU / 128 MiB, frontend — 0,25 CPU / 64 MiB. Запустил 12-секундный CPU-цикл внутри backend-контейнера и шесть раз запросил `GET /healthz` во время нагрузки.

| Наблюдение | Результат | Метод |
|---|---:|---|
| Backend CPU при нагрузке | около 49,6–52,1% одного CPU | `docker stats`; задан лимит 0,50 CPU |
| Backend RAM при нагрузке | около 44,0–44,6 MiB из 128 MiB | `docker stats` |
| `/healthz` во время цикла | 200; 35–95 ms в шести последовательных запросах | `curl` с измерением времени на локальном Mac |
| Троттлинг за замер | `nr_throttled`: 200 → 321; `throttled_usec`: 10 412 466 → 17 430 192 | `/sys/fs/cgroup/cpu.stat` внутри backend |
| Тесный лимит памяти | отдельный `resource-probe` достиг 64 MiB и завершился `OOMKilled`, exit 137 | изолированный Compose-профиль `lab-02-probe`, без сети |

Порог 64 MiB относится только к одноразовому изолированному probe: он показывает реакцию контейнера на тесный лимит, но не устойчивость приложения. Сам backend под исследованной CPU-нагрузкой оставался healthy при лимитах 0,50 CPU / 128 MiB; его замеренная память была ниже установленного предела. Более тяжёлый или длительный рабочий профиль этим коротким опытом не проверялся.

Два опыта нельзя свести к фразе «контейнер выдержал лимиты». Под ограничением CPU backend продолжал отвечать; в отдельном опыте с памятью завершился одноразовый probe. Это разные процессы, разные ограничения и разные критерии результата.

Если главным достижением считать только низкое потребление, у завершившегося probe есть сильная заявка на победу: он уже не просит добавки. Следующий шаг такой оптимизации — вообще не запускать сервис и гордо защищать нулевой бюджет. Пользователя тогда тоже придётся включить в список необязательных зависимостей. Поэтому рядом с цифрой лимита нужен результат полезной работы: здесь это шесть ответов health под CPU-нагрузкой. Уменьшение потребления после OOM отдельно не измерялось; рассуждение про нулевой бюджет — продолжение заведомо неполного критерия, а не выполненный опыт.

После опыта OOM probe удалён, сервисы приложения оставлены запущенными. Данные БД не очищались. Для воспроизведения используйте команды запуска и остановки из [инструкции ЛР2](../lab-02/README.md); для дополнительного изолированного OOM-теста см. команды в [evidence/runtime-checks.txt](evidence/runtime-checks.txt).

## Нагрузка API и подбор лимитов — 28 октября 2026 года

Полный опыт выполнен на Mac ARM64 с Docker Desktop 4.87.0, Docker Engine 29.7.2 и Compose 5.4.0, с 16:19:53 до 16:24:36 UTC. Приложение собрано локально из рабочего дерева с HEAD `58f9afb`; исходники runner и экспериментального Compose на момент запуска сохранены рядом с [результатами](evidence/2026-10-28-resource-experiment-bec2ca/README.md). Эти измерения не заменяют Docker benchmark ЛР2 на `e4e356f`.

Стенд `lab02star-20261028-bec2ca` содержал собственные frontend, backend и PostgreSQL, отдельные сети и том. Frontend получил свободный порт на `127.0.0.1`; порты backend и БД на хост не публиковались. В этом проекте задано `restart: "no"`, чтобы после OOM сохранить завершившийся контейнер для inspect. В БД через API создана контрольная задача, затем добавлены 4 000 фиктивных задач с заголовками по 200 символов. Восемь клиентов одновременно выполняли `GET /api/tasks` и полностью читали ответ примерно 1,08 MB. Код приложения для нагрузки не менялся; память расходовали чтение строк из PostgreSQL и формирование JSON.

### Как выбран нагружаемый сервис

В baseline на всех трёх сервисах снимался `docker stats`. По пяти отсчётам во время одной и той же API-нагрузки получились следующие значения:

| Сервис | Максимальный CPU в отсчётах | RAM до нагрузки → максимум | Прирост RAM |
|---|---:|---:|---:|
| PostgreSQL | 18,66% | 25,74 → 37,54 MiB | 11,80 MiB |
| Backend | 50,26% | 42,55 → 76,78 MiB | 34,23 MiB |
| Frontend | 5,08% | 11,66 → 13,65 MiB | 1,99 MiB |

Backend оказался наиболее нагруженным и по CPU, и по приросту памяти, поэтому его лимиты менялись в следующих фазах. БД оставалась на 0,50 CPU / 256 MiB, frontend — на 0,25 CPU / 64 MiB. Исходные отсчёты сохранены в [docker-stats.csv](evidence/2026-10-28-resource-experiment-bec2ca/docker-stats.csv).

### Тесные и рабочие пределы

| Фаза backend | Нагрузка | Наблюдение | Результат |
|---|---|---|---|
| 0,10 CPU / 256 MiB | 30 с запуска запросов, 8 клиентов | 97 ответов 200, ошибок нет; медиана 2 504,4 ms; CPU до 10,38% | API отвечает, но CPU ограничивает обработку |
| 0,50 CPU / 256 MiB | Те же 30 с и 8 клиентов | 962 ответа 200, ошибок нет; медиана 220,5 ms; CPU до 50,95% | Увеличение CPU сократило задержки в этом опыте |
| 0,50 CPU / 64 MiB, без swap | Те же 30 с и 8 клиентов | После healthy: 8 ответов 200, 114 ответов 502 и 24 транспортные ошибки; backend завершился `OOMKilled=true`, exit 137 | Памяти недостаточно для этой нагрузки |
| 0,50 CPU / 128 MiB | 60 с, те же 8 клиентов и данные | 1 907 ответов 200, ноль ошибок и таймаутов; медиана 221,6 ms; RAM до 101,10 MiB; после нагрузки healthy | Первый рабочий кандидат прошёл; 256/512 MiB далее не испытывались |

Во время фазы 0,10 CPU счётчик cgroup `nr_throttled` вырос 139 → 477, `throttled_usec` — 16 398 361 → 110 631 772. При 0,50 CPU throttling тоже наблюдался: 10 → 311 и 495 746 → 65 888 486. Увеличение лимита не означает исчезновения ограничения; сравниваются счётчики и фактические ответы API. [JSON CPU-фазы 0,10](evidence/2026-10-28-resource-experiment-bec2ca/cpu-010-30s.json) и [0,50](evidence/2026-10-28-resource-experiment-bec2ca/cpu-050-30s.json) содержат исходные значения.

OOM относится к самому контейнеру backend: до нагрузки он был healthy, после неё Docker зафиксировал `OOMKilled=true`, exit 137 и `restart_count=0`. В inspect записаны фактические `Memory=67108864` и `MemorySwap=67108864`. Это [проверяемое состояние после отказа](evidence/2026-10-28-resource-experiment-bec2ca/oom-after-load-backend-inspect.json), а не вывод из одного HTTP 502. Периодический `docker stats` не успел снять живой пик этой короткой OOM-фазы; нулевые отсчёты после остановки не показывают расход памяти перед отказом. Все ошибки фазы сохранены в [её JSON](evidence/2026-10-28-resource-experiment-bec2ca/oom-064m-30s.json): счётчик полный, примеры первых двадцати ошибок ограничены по объёму.

Окно запуска запросов и время завершения всех начатых запросов различаются. Для CPU-фаз второе составило 34,495 и 31,001 с, для OOM — 37,066 с, для рабочего прохода — 60,173 с. Это указано в `elapsed_seconds`; отсчёты `docker stats` являются выборкой, а не непрерывной записью пиков. [Рабочая фаза](evidence/2026-10-28-resource-experiment-bec2ca/working-128m-60s.json) прошла без OOM и перезапусков. Найденные 128 MiB относятся к этому набору данных и восьми клиентам; более тяжёлый профиль не проверялся.

### Данные и очистка

При смене лимитов пересоздавались только backend и frontend с `--no-deps`. После OOM и рабочего прохода API вернул ту же контрольную задачу: id `1`, title `lab02-star-control-lab02star-20261028-bec2ca` и прежний `created_at`. Контейнер PostgreSQL и имя/дата создания тома совпали до и после фаз.

После проверки удалены только экспериментальные контейнеры, сети, том и уникальные теги образов. Идентификаторы четырёх контейнеров основного стека и ранее существовавшего `lab4-postgres` не изменились. В [summary.json](evidence/2026-10-28-resource-experiment-bec2ca/summary.json) сохранены сравнения, `accepted=true` и пустой список `acceptance_failures`; [транскрипт команд](evidence/2026-10-28-resource-experiment-bec2ca/commands.txt) содержит фактический ход опыта и cleanup.

Повторение из корня репозитория:

```sh
python3 scripts/lab-02-star-experiment.py
```

[Runner](../../scripts/lab-02-star-experiment.py) каждый раз создаёт собственный project, временный пароль и отдельную БД по [экспериментальному Compose](experiment.compose.yaml). Результат записывается в новый каталог evidence; после проверки свои ресурсы удаляются. Основной `compose.yaml` в этом опыте не используется.
