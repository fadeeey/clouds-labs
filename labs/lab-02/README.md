# ЛР2 — Docker и Compose

В ЛР2 сравниваются два рецепта сборки одного backend: намеренно плохой и исправленный. Затем проверяется Compose-стек из frontend, backend и отдельной PostgreSQL: кто с кем связан по сети, от какого пользователя работает процесс и где остаются данные после пересоздания контейнеров.

## Актуальный запуск

Для текущей версии проекта используйте [быстрый запуск в корневом README](../../README.md#запуск). Он включает создание `.env`, локальных TLS/Basic Auth файлов и запуск актуального Compose-стека. Старые команды запуска не копируйте отдельно: они не создают все локальные файлы текущей ЛР1.

Последовательность команд и конфигурация на момент измерений ЛР2 сохранены в [README этой лабораторной на ревизии `e4e356f`](https://github.com/fadeeey/clouds-labs/blob/e4e356f/labs/lab-02/README.md). Значения размера и времени сборки тоже сняты на этой ревизии; поздние изменения базового образа и приложения относятся к ЛР3.

## Что сравнивалось

`docker/lab-02/Dockerfile.bad` показывает плавающую версию Python, запуск от root и копирование контекста до установки зависимостей; в нём также нет multi-stage-сборки и `HEALTHCHECK`. Корневой `.dockerignore` применяется к обоим вариантам. В `Dockerfile.good` закреплён digest multi-arch образа, зависимости отделены от кода, а runtime работает от пользователя `app`.

| Образ | `docker image inspect .Size` | Изменение одной строки HTML, тёплый кэш |
|---|---:|---:|
| bad | 421 400 431 B (401,9 MiB) | 7,16 с |
| good | 53 626 340 B (51,1 MiB) | 0,31 с |

В таблице — поле `.Size` локального ARM64 image и один замер повторной сборки на [ревизии `e4e356f`](https://github.com/fadeeey/clouds-labs/commit/e4e356f). Объём загрузки не измерялся. Оба варианта собирались одним `default` Buildx builder; после правки HTML в bad снова выполнялся `pip install`, в good использовался кэш зависимостей. Эти числа нельзя переносить на текущий HEAD или другую машину.

## Результат

- В измеренной версии Compose поднимал три сервиса: frontend, backend и отдельную PostgreSQL. Текущая версия с двумя backend запускается по корневой инструкции.
- Backend работает от `app`; frontend не подключён к внутренней сети базы.
- Запись, добавленная через API, сохранилась после перезапуска сервисов без удаления тома.
- [Отчёт с проверками и снимком работающего интерфейса](report.md).

В bad перед установкой зависимостей стоит `COPY . .`: сборщик получает весь проект как основание для следующего шага. Жалоба «зачем ты трогал пакеты из-за HTML?» звучит разумно, пока не перечитаешь собственный рецепт. BuildKit не проявил лишней инициативы — её заранее включили в инструкцию. В good `requirements.txt` копируется отдельно, и правка страницы больше не даёт повода повторять установку.
