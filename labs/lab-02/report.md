# ЛР2 — сборка образа и Compose

Нужно сравнить плохой и исправленный Dockerfile, затем проверить работу frontend, backend и PostgreSQL в Compose. Важны не только размер образа и время сборки: приложение должно работать от отдельного пользователя, сети — ограничивать доступ, а данные — переживать пересоздание контейнеров.

Все измерения ниже относятся к исторической ревизии `e4e356f` на `linux/arm64`. Состав Compose и результаты сборки в этом отчёте не описывают текущий HEAD.

## Сборка и измерения

Оба образа собирались одним builder на `linux/arm64`:

```sh
docker --context=default buildx build --builder default --platform linux/arm64 --load -f docker/lab-02/Dockerfile.bad -t clouds-lab-backend:bad .
docker --context=default buildx build --builder default --platform linux/arm64 --load -f docker/lab-02/Dockerfile.good -t clouds-lab-backend:good .
```

Размеры сняты после сборки через `docker image inspect --format '{{.Size}}' <image>`:

| Вариант | Фактическое `.Size` | Пересчёт в MiB |
|---|---:|---:|
| bad | 421 400 431 B | 401,9 MiB |
| good | 53 626 340 B | 51,1 MiB |

Уменьшение по этому методу — около 87,3%. Значение `.Size` относится к локальному образу; объём скачиваемых слоёв отдельно не измерялся.

Для замера повторной сборки я добавил точку к `Учебные задачи` в заголовке `app/frontend/index.html`, замерил команды с ` /usr/bin/time -p`, а затем вернул исходную строку. Сборка bad заняла 7,16 с: после изменения контекста BuildKit повторно выполнил `pip install -r requirements.txt`. Сборка good заняла 0,31 с: слой с зависимостями остался в кэше, пересобрался только слой frontend-файлов. Это один исторический замер на локальном Mac с тёплым кэшем. Он показывает различие в использовании слоёв; такое время для другой машины, холодного кэша или текущей версии приложения не обещается.

На этом месте удобно обвинить сборщик в чрезмерной реакции: изменился заголовок страницы, а он опять устанавливает пакеты. Но в bad перед установкой стоит `COPY . .`. Это я положил весь проект перед `pip install` и тем самым объявил каждый файл основанием для повторного выполнения следующих шагов.

Претензия к Docker получилась бы необычная: прошу перестать так точно выполнять мои инструкции. У сборщика нет повода угадывать, что HTML сегодня несущественен, а `requirements.txt` важен. В good эта разница прямо записана порядком `COPY`: сначала отдельный файл зависимостей, потом код. После изменения рецепта BuildKit сохранил слой пакетов. Инструмент тот же; из эксперимента исчезла моя просьба делать лишнюю работу.

## Compose и проверки

В `compose.yaml` измеренной версии работают три сервиса. `frontend` находится в сети `frontend`; `backend` подключён к `frontend` и `database`; PostgreSQL подключён только к `database`. У БД есть именованный том `postgres_data`.

| Проверка | Наблюдение | Доказательство |
|---|---|---|
| Состав Compose | `db` и `backend` — `healthy`, `frontend` — `Up` | `docker compose ps` |
| Готовность БД через API | `{"database":"ok","status":"ok"}` | `curl -fsS http://127.0.0.1:5001/health` |
| Пользователь backend | `app` | `docker compose exec backend whoami` |
| Frontend не видит БД по сети | `wget: bad address 'db:5432'` | команда из README; frontend не подключён к `database` |
| Сохранение данных | запись с ID 6 осталась после удаления и повторного создания контейнеров | POST через `http://127.0.0.1:8080/api/tasks`, `docker compose down`, `docker compose up -d --no-build`, GET того же API |
| Интерфейс | Nginx отдаёт HTML, CSS и JS с кодом 200; статус «БАЗА НА СВЯЗИ» | [Снимок работающего интерфейса](evidence/app-compose.png) |
| Тесты API | 3/3 прошли с реальной PostgreSQL | `tests/test_api.py` запущен внутри backend-контейнера, где доступно имя БД `db` |

Первый снимок выявил отдельную проблему: HTML загружался, но `/assets/styles.css` и `/assets/app.js` возвращали 404. В `docker/lab-02/nginx.conf` добавлено правило для `/assets/`; после пересборки frontend все три URL вернули 200, а в браузере отобразились стили и данные из PostgreSQL.

Запуск той же интеграционной проверки с хоста через `127.0.0.1:5433` не прошёл: порт указан в Compose, но в этой среде соединение с macOS получило `Connection refused`. Поэтому тесты выполнялись внутри backend-контейнера по внутренней сети; прямое подключение с хоста не заявляю как проверенное.

## Итог и границы

Обычный `docker compose down` и повторный запуск сохранили запись в `postgres_data`. На момент этой обычной ЛР2 (коммит `e4e356f`) в Compose ещё не было автоматического восстановления после падения, лимитов CPU/RAM и сценария OOM; эти проверки выполнены отдельно в [отчёте ЛР2*](../lab-02-star/report.md).
