# ЛР1* — проверки конфигурации Nginx

## Цель и границы

Методичка предлагает «попробовать „взломать“ nginx любого доступного сайта» и «проверить минимум три уязвимости», рекомендуя выбрать «что-то небольшое локальное» (Лаба 1, абз. 38–43, [условие в Google Drive](https://drive.google.com/file/d/19LNpEpXeLxTAPDgKczQPlA44Lc7e9Tgt/view)). Успешность эксплуатации на оценку не влияет. Основной объект проверки — собственный работающий сайт из ЛР1: на нём проверены доступ к dotfile, path traversal и доступ к закрытому маршруту без авторизации. Отдельный намеренно уязвимый Nginx-стенд оставлен дополнительной демонстрацией ошибок.

Все адреса локальные и принадлежат нашему стенду. Запросы выполнялись без паролей, DDoS и подбора учётных данных; чужие сайты не проверялись. Формулировка «любой доступный сайт» прямо не запрещает собственный сайт, но отдельного согласования такого объекта в этом отчёте нет.

## Проверки работающего сайта — 28 октября 2026 года

| Проверка | Запрос к `https://localhost:8443` | Наблюдение | Итог попытки |
|---|---|---|---|
| Выдача dotfile | `GET /.env` | HTTP 404 | Запрошенный скрытый файл не выдан |
| Path traversal | `GET /docs/../../etc/passwd` с `--path-as-is` | HTTP 400 | Запрос с выходом за каталог отклонён |
| Доступ без авторизации | `GET /admin` без учётных данных | HTTP 401 | Для закрытого маршрута потребовалась авторизация |

[Фактические коды ответов](evidence/2026-10-28-live-nginx-checks.txt) получены тремя короткими GET-запросами. Тела и заголовки ответов не сохранялись, учётные данные не передавались. В этих попытках получить закрытые данные не удалось. Три результата относятся к указанным URL; они не доказывают отсутствие других способов обхода конфигурации.

## Дополнительная демонстрация ошибок — 20 октября 2026 года

Для контролируемого воспроизведения использовался отдельный Nginx с фиктивными файлами. Исторический запуск слушал `127.0.0.1:18081`, данные были смонтированы только для чтения; после проверки контейнер и сеть удалены. Актуальный скрипт назначает свободный loopback-порт, создаёт временную копию fixtures и формирует `/.env` из тестового шаблона, не используя локальный игнорируемый `.env`.

| Проверка | Запрос | Наблюдение | Вывод |
|---|---|---|---|
| Path traversal через некорректный `alias` | `GET /img../secret.txt` с `curl --path-as-is` | HTTP 200 и `TRAVERSAL_FIXTURE=only-for-local-lab` | location `/img` без завершающего `/` позволяет выйти из каталога `images` к соседнему фиктивному файлу |
| Открытый листинг резервной папки | `GET /backup/` | HTTP 200, в выдаче имя `backup-note.txt` | `autoindex on` раскрывает структуру и имена файлов |
| Доступ к dotfile | `GET /.env` | HTTP 200 и `TEST_FIXTURE_ONLY=1` | нет запрета на выдачу скрытых файлов; содержимое полностью фиктивное |

Во всех трёх строках ожидается HTTP 200 с конкретным фиктивным содержимым. Скрипт проверяет не пригодность Nginx к эксплуатации, а воспроизводимость каждой ошибки. Поэтому его успешное завершение не означает, что конфигурация защищена.

После обычной ЛР1 хочется действовать решительно: закрыть `/.env`, убрать листинг, поправить `alias`. Здесь такая полезная инициатива испортила бы опыт. Пришлось бы разбирать падение теста и писать до странности убедительное объяснение, зачем вернуть доступ к файлу с именем `.env`. Снаружи это выглядело бы как очень неудачное ревью по безопасности. Внутри изолированного fixture это требование к контрольному образцу: ошибка должна оставаться ошибкой, чтобы её обнаружение можно было проверить.

Строки `TRAVERSAL_FIXTURE=only-for-local-lab` и `TEST_FIXTURE_ONLY=1` позволяют распознать именно учебные ответы. Реальных секретов за ними нет.

Каждый ответ сохранён как скриншот: [path traversal](evidence/path-traversal.png), [листинг](evidence/directory-listing.png), [dotfile](evidence/dotfile-exposure.png). Команда для повторения всех трёх попыток — [scripts/lab-01-star-check.sh](../../scripts/lab-01-star-check.sh); её фактический краткий вывод сохранён в [evidence/check-output.txt](evidence/check-output.txt). Файлы стенда находятся рядом в `nginx.conf` и `fixtures/` и явно помечены как учебные.

## Дополнительные проверки основного приложения 20 октября

Уязвимый стенд не подключён к основному Compose. В основном Nginx проверил соответствующие защиты: `/docs/../404.html` вернул собственный 404, `/.env` вернул 404, а `/docs/` без индексного файла вернул 403 вместо списка. В ЛР1 также проверено, что `/admin` отвечает 401 без Basic Auth. Эти результаты относятся к текущему конфигу приложения и не являются доказательством абсолютной безопасности.

В результате воспроизведены три ошибки и отдельно проверены соответствующие ограничения основного приложения. После опытов основной Compose-стек остался доступен; временные Nginx-контейнер и сеть удалены. Три коротких запроса к локальному fixture не были сканированием внешних адресов или аудитом всего приложения.
