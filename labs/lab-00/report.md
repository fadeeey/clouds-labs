# ЛР0 — полевой журнал

## Задача

Нужно создать небольшой frontend/backend-сервис с отдельной сетевой БД. Для проверки выбрал журнал учебных задач: одна форма создаёт запись, один список показывает результат. Успех — не только появление строки после нажатия кнопки, но и чтение той же записи после обновления страницы и перезапуска PostgreSQL.

## Решение

Интерфейс состоит из отдельных HTML/CSS/JS-файлов и обращается к API по тому же origin. Flask отдаёт страницу и обрабатывает `/api/tasks`; PostgreSQL работает отдельным Docker Compose-сервисом с именованным томом. SQLite не используется. В версии ЛР0 Flask сам отдаёт frontend-файлы, без отдельного веб-сервера; БД остаётся самостоятельным сетевым сервисом.

Проверка намеренно начинается в браузере, а заканчивается после перезапуска БД. Иначе можно убедительно показать кнопку «Сохранить», не выяснив, кто именно согласился что-либо хранить.

## Проверка: ожидание, наблюдение, доказательство

| Ожидание | Наблюдение | Доказательство |
|---|---|---|
| Новая задача проходит через форму и API | Через форму добавлена «Проверка Л0: задача переживает обновление страницы»; интерфейс показал её в списке | [Скриншот после обновления страницы](evidence/app-created-task.png); интеграционный тест `test_task_round_trip_persists_in_postgres` проверяет HTTP POST, затем GET |
| Backend действительно видит БД | `/health` выполнил `SELECT 1` и ответил `{"database":"ok","status":"ok"}` | Реальный `curl -fsS http://127.0.0.1:5000/health`; интеграционный тест `test_health_checks_real_database` |
| Запись остаётся после обновления страницы и перезапуска БД | После reload та же задача осталась в интерфейсе; после `docker compose restart db` контейнер снова стал `healthy`, API вернул ту же запись | Браузерная проверка и последующий `GET /api/tasks`; Compose использует именованный том `postgres_data` |
| Пустая задача не записывается | API вернул `400` для строки из пробелов | `test_blank_task_is_rejected` |

Тесты запускались так:

```sh
python -m unittest discover -s tests -v
```

Фактический результат: `Ran 3 tests ... OK`. Перед этим контейнер `postgres:17.6-alpine` перешёл в `healthy`.

После создания контрольной задачи обновили страницу, затем перезапустили PostgreSQL. API снова вернул ту же запись. У зрителя три почти одинаковых кадра; у проверки — три разных основания считать строку сохранённой. Сначала её показал интерфейс после POST, затем она пришла новым GET, а потом пережила перезапуск процесса БД.

Такой результат неудобно демонстрировать: запускаешь проверку, ждёшь возвращения контейнера — и торжественно показываешь всё ту же задачу. Кнопка «Добавить» хотя бы что-то меняет на экране. Здесь большая часть доказательной работы ушла на то, чтобы никакого нового сюжета не появилось.

## Итог и границы

Frontend → Flask API → отдельная PostgreSQL работает; запись создаётся через браузер, читается после reload и пережила перезапуск контейнера БД. Команды запуска и остановки находятся в корневом [README](../../README.md), разбор частей и условий запуска — в [инструкции ЛР0](README.md).

Результат относится к версии ЛР0 с отдельной PostgreSQL. Nginx, две копии backend, сборка образа приложения, CI/CD и публичный deployment в этот опыт не входили. Сохранение одной записи после одного перезапуска также не заменяет проверку резервного копирования.
